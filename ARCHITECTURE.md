# Архитектура Investing Demo

## 1. Назначение и технологический стек

Investing Demo — серверное веб-приложение для просмотра списка акций, их текущих котировок и графика исторических цен. Пользователь может зарегистрироваться и войти в систему; авторизованным пользователям доступны операции управления акциями через веб-интерфейс. Для программного доступа предусмотрен REST API.

Основной стек:

- Python и Django 5.2 — веб-приложение, маршрутизация, шаблоны, ORM и аутентификация.
- SQLite — база по умолчанию для локального запуска; PostgreSQL включается через переменные окружения.
- Django REST Framework — REST API и сериализация моделей.
- Celery и Redis — периодическое выполнение фоновой задачи обновления котировок; Redis используется как брокер.
- Tinkoff Invest SDK — необязательная интеграция из архивированного официального GitHub-репозитория; получение справочника акций, последних цен и исторических свечей.
- Plotly — построение графика исторических цен.
- Bootstrap — CSS-оформление серверных HTML-шаблонов.

Приложение запускается как Django/WSGI-сервис. В проекте также есть ASGI-конфигурация, однако отдельный ASGI-сервер или асинхронная обработка в коде не настроены.

## 2. Структура проекта

- `config/` — настройки Django и инфраструктурная конфигурация:
  - `settings.py` — подключенные приложения, middleware, база данных, REST Framework, журналирование и параметры Celery.
  - `urls.py` — корневые маршруты.
  - `celery.py` — создание Celery-приложения и расписание периодической задачи.
  - `wsgi.py`, `asgi.py` — точки входа веб-приложения.
- `dashboard/` — функциональность акций:
  - `models.py` — модель `Share`.
  - `views.py`, `urls.py`, `forms.py` — HTML-страницы и CRUD-формы.
  - `api/` — REST API, ViewSet, сериализатор и маршруты версии 1.
  - `services/market_data.py` — обращение к API Tinkoff за последней ценой.
  - `services/graph.py` — получение исторических свечей и формирование графика Plotly.
  - `tasks.py` — фоновое обновление цены и направления тренда.
  - `management/commands/add_shares.py` — команда начального импорта акций из Tinkoff.
  - `migrations/` — история изменений схемы базы данных.
  - `templates/`, `static/` — HTML-шаблоны и локальные статические ресурсы.
- `user/` — формы и представления регистрации, входа и выхода. Отдельная пользовательская модель в приложении не определена.
- `manage.py` — CLI для команд Django, включая миграции, запуск сервера и команду импорта.
- `docker-compose.yml` — конфигурации контейнеров PostgreSQL и Redis.
- `requirements.txt` — диапазоны версий обязательных Python-зависимостей.
- `requirements-market-data.txt` — зависимости интеграции с SDK; сам SDK устанавливается из исходников отдельно.

## 3. Архитектура и взаимодействие компонентов

Приложение организовано как монолит на Django с двумя функциональными приложениями (`dashboard` и `user`). Представления используют Django ORM напрямую; отдельного слоя бизнес-сервисов для операций CRUD нет. Сервисные модули выделены для интеграции с поставщиком рыночных данных и построения графика.

Основной поток веб-запроса:

1. `config/urls.py` направляет запрос в `dashboard.urls` или `user.urls`.
2. Представление формирует ответ: HTML на основе шаблона либо данные API.
3. При необходимости представление обращается к модели через Django ORM, а ORM выполняет запрос к выбранной базе данных.
4. При открытии страницы одной акции `ShareDetailView` также вызывает `get_graph`: сервис получает дневные свечи за последние 180 дней у Tinkoff и формирует HTML-фрагмент Plotly для шаблона.

Поток фонового обновления:

1. Celery Beat из `config/celery.py` запускает `dashboard.tasks.update_last_price`.
2. Задача выбирает акции из базы данных и для каждой вызывает `get_last_data`.
3. Сервис запрашивает последнюю цену у Tinkoff.
4. Задача сравнивает её с сохраненной ценой, записывает цену и признак роста в PostgreSQL.

Поток REST API:

1. Маршрут `/api/v1/shares/` проходит через корневой URL, `dashboard.urls`, `dashboard.api.urls` и маршрутизатор DRF.
2. `ShareViewSet` использует `Share` и `ShareSerializer`, предоставляя стандартные операции ModelViewSet: список, получение одной записи, создание, изменение и удаление.
3. По настройкам DRF список разбивается на страницы по 100 записей. Поддерживаются фильтрация по `name` и `ticker`, сортировка по этим полям, а также поиск по `name`.

В `docker-compose.yml` описаны только база и Redis. Веб-приложение, Celery Worker и Celery Beat запускаются отдельно командами, указанными в `README.md`.

## 5. Модель данных

### `Share`

Модель находится в `dashboard/models.py` и представляет акцию:

| Поле | Тип | Назначение и ограничения |
|---|---|---|
| `id` | `BigAutoField` | Первичный ключ Django |
| `figi` | `CharField(255)` | Идентификатор инструмента Tinkoff, уникальный |
| `isin` | `CharField(255)` | Международный идентификатор ценной бумаги |
| `name` | `CharField(255)` | Наименование компании |
| `ticker` | `CharField(10)` | Биржевой тикер, уникальный |
| `currency` | `CharField(20)` | Валюта котировки |
| `uid` | `CharField(255)` | UID инструмента Tinkoff, уникальный |
| `last_price` | `FloatField`, nullable | Сохраненная текущая цена |
| `is_trend_high` | `BooleanField`, nullable | Признак роста относительно предыдущей сохраненной цены |
| `updated_at` | `DateTimeField`, nullable, `auto_now=True` | Время обновления при сохранении экземпляра модели |

### Персональный мониторинг

- `WatchlistItem` связывает стандартного пользователя Django с акцией. Уникальное ограничение не позволяет добавить одну и ту же акцию в список пользователя дважды.
- `PriceAlert` принадлежит записи мониторинга и хранит положительную целевую цену, статус активности и сторону уровня, на которой цена наблюдалась в прошлый раз. Повтор целевого уровня для одной акции в списке запрещён.
- `AlertNotification` хранит цену и время пересечения, а также время прочтения. Владелец определяется через связанные `PriceAlert` и `WatchlistItem`.

Записи мониторинга изолированы по пользователям; удаление акции из списка каскадно удаляет её уровни и уведомления.

### Пользователи

Приложение `user` использует модель, возвращаемую `get_user_model()`. В проекте не задан `AUTH_USER_MODEL`, поэтому используется стандартная модель `django.contrib.auth.User`. Регистрационная форма создает пользователя, используя адрес электронной почты в качестве имени пользователя и адреса email.

## 6. Обработка запросов и работа с базой данных

- **HTML-интерфейс:** Django class-based views отображают список акций с пагинацией, страницу отдельной акции, а также формы создания, редактирования и удаления. Формы акций построены на `ModelForm`. Для операций создания, изменения и удаления используется проверка аутентификации; список и просмотр доступны без входа.
- **Аутентификация:** пользовательские представления обрабатывают регистрацию и вход по email/паролю, вызывая стандартные механизмы Django `authenticate`, `login` и `logout`.
- **REST API:** DRF ModelViewSet выполняет CRUD через ORM. В `REST_FRAMEWORK` заданы пагинация limit/offset с размером страницы 100 и backend `django-filter`. Чтение доступно анонимно; изменение данных требует аутентификации.
- **Поставщик данных:** интеграция с Tinkoff используется в команде импорта, задаче обновления цен и при запросе графика. SDK загружается лениво; токен читается из переменной окружения `TINKOFF_TOKEN`.
- **Ценовые оповещения:** после сохранения очередной котировки задача вызывает `dashboard.services.price_alerts.process_price_alerts`. Сервис транзакционно сравнивает наблюдаемую сторону каждого активного уровня с предыдущей; пересечение создаёт внутреннее уведомление, повторное наблюдение с той же стороны — нет.
- **Запуск фоновых задач:** Redis указан как брокер по умолчанию `redis://127.0.0.1:6379/0`, URL можно переопределить через `CELERY_BROKER_URL`. Celery Beat запускает обновление каждые 10 секунд. Worker и Beat запускаются отдельно.
- **База данных:** Django использует SQLite по умолчанию. Для PostgreSQL задается `DB_ENGINE=postgresql` и переменные `POSTGRES_*`; Compose создает PostgreSQL 16 с именованным томом и Redis 7, но не контейнер приложения.
- **Конфигурация:** секрет Django, режим DEBUG и разрешенные хосты задаются переменными окружения; при отключенном DEBUG требуется `DJANGO_SECRET_KEY`.

## 7. Наблюдения о фактической реализации

- Для локального запуска используются DEBUG и демонстрационный SECRET_KEY; production-значения задаются окружением, а пустой токен внешнего API не препятствует запуску сайта.
- Настройки базы, токена и брокера теперь читаются из окружения; конфигурация Compose использует фиксированные основные версии PostgreSQL и Redis и постоянный том базы данных.
- Задача запускается каждые 10 секунд. Ошибки обработки отдельной акции логируются с traceback, после чего задача продолжает цикл.
- Задача сохраняет цену через экземпляр модели, поэтому `updated_at` обновляется автоматически.
- В коде нет отдельной таблицы истории котировок. Исторический график каждый раз запрашивается у Tinkoff, тогда как в базе хранится только последнее значение цены и признак тренда.
