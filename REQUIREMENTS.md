которые только подразумеваются или перечислены в задании №4 (watchlist,

шаблоны.

Статусы требований:

| Статус | Значение |
|---|---|
| **Р** | реализовано в коде |
| **РД** | реализовано, но содержит дефект, влияющий на сценарий |
| **О** | реализовано как ограничение/особенность поведения |

Дефекты не формулируются как требования. Они вынесены в раздел 7 и не должны
использоваться как основание для проектирования новой функциональности без

## 3. Основные сценарии взаимодействия

### UC-01. Просмотр каталога акций

**Актор:** гость или аутентифицированный пользователь.  
**Предусловие:** в БД есть хотя бы одна запись `Share`; иначе выводится сообщение
«Акций еще нет».

**Основной поток:**

1. Пользователь открывает `GET /`.
2. `ShareListView` выбирает все акции, сортирует по `name` и разбивает на
   страницы по 100.
3. Шаблон выводит тикер, название, ISIN, текущую цену с валютой и цвет фона:
   зелёный при `is_trend_high = True`, розовый в остальных случаях.
4. Для аутентифицированного пользователя дополнительно выводятся кнопки
   «Добавить», «Редактировать», «Удалить» и колонка «Управление».

**Альтернативы:**

- Каталог пуст → выводится «Акций еще нет» (`list.html:83-85`).
- Пользователь не аутентифицирован → кнопки управления скрыты
  (`list.html:9-13, 23-25, 41-50`).

**Подтверждение:** `dashboard/views.py:20-26`, `dashboard/templates/dashboard/list.html:15-85`.

### UC-02. Просмотр карточки акции и графика

**Актор:** гость или аутентифицированный пользователь.  
**Предусловие:** акция с указанным `id` существует.

**Основной поток:**

1. Пользователь открывает `GET /<pk>`.
2. `ShareDetailView` загружает `Share` по `id`.
3. Сервис `get_graph` запрашивает дневные свечи за последние 180 дней по `figi`.
4. Формируется HTML-фрагмент Plotly с линейным графиком цен закрытия.
5. Шаблон выводит название, текущую цену, валюту, время обновления и график.

**Исключения:**

- Акция не найдена → `Share.DoesNotExist` не обрабатывается, ответ 500
  (дефект D-04).
- Tinkoff API недоступен → исключение не обрабатывается в представлении,
  запрос завершается ошибкой (дефект D-17).

**Подтверждение:** `dashboard/views.py:29-38`, `dashboard/templates/dashboard/detail.html:8-28`, `dashboard/services/graph.py:11-36`.

### UC-03. Регистрация пользователя

**Актор:** гость.  
**Предусловие:** пользователь с таким email ещё не зарегистрирован.

**Основной поток:**

1. Пользователь открывает `GET /user/registration/`; отображается страница
   регистрации с полями Email, «Пароль», «Повторите пароль».
2. Пользователь отправляет `POST` с `email`, `password1`, `password2`.
3. Форма проверяет обязательность полей и совпадение паролей.
4. Форма проверяет отсутствие пользователя с таким email.
5. Создаётся пользователь: `username = email`, `email = email`, пароль
   сохраняется в виде хэша.
6. Выполняется автоматический вход и редирект на `/`.

**Альтернативы и исключения:**

- Пароли не совпадают → выбрасывается `ValidationError` с сообщением
  «Введенные пароли не совпадают».
- Email уже зарегистрирован → `ValidationError` с сообщением о необходимости
  войти или использовать другой email.
- Ошибка уровня поля (например, пустой email) → попытка обратиться к
  `form.errors["__all__"]` может привести к `KeyError` и 500 (дефект D-02).
- На GET в контекст передаётся класс формы, а не экземпляр, поэтому поля могут
  отображаться некорректно (дефект D-01).

**Подтверждение:** `user/views.py:36-55`, `user/forms.py:8-53`, `user/templates/user/registration.html:4-24`.

### UC-04. Вход в систему

**Актор:** гость.  
**Предусловие:** пользователь зарегистрирован.

**Основной поток:**

1. Пользователь открывает `GET /user/login/`.
2. Отправляет `POST` с `email` и `password`.
3. Представление приводит email к нижнему регистру и вызывает
   `authenticate(username=email, password=password)`.
4. При успехе выполняется `login()`, создаётся сессия, выполняется редирект на `/`.
5. При неудаче страница входа повторно отображается с сообщением «Неверный логин
   или пароль! Повторите попытку.».

**Исключения:**

- Поля отсутствуют в POST → `KeyError`, так как `form.is_valid()` не вызывается
  (дефект D-03).
- Email зарегистрирован в смешанном регистре → вход может не работать, поскольку
  при регистрации регистр не нормализуется, а при входе — нормализуется
  (дефект D-15).

**Подтверждение:** `user/views.py:8-33`, `user/forms.py:56-70`, `user/templates/user/auth.html:3-20`.

### UC-09. Работа с REST API

**Актор:** любой клиент, включая анонимного.  
**Предусловие:** приложение запущено, БД доступна.

**Поток:**

1. `GET /api/v1/shares/` возвращает постраничный список акций.
2. `GET /api/v1/shares/{id}/` возвращает одну акцию.
3. `POST /api/v1/shares/` создаёт акцию по полям сериализатора.
4. `PUT/PATCH /api/v1/shares/{id}/` обновляет акцию.
5. `DELETE /api/v1/shares/{id}/` удаляет акцию.
6. `GET /api/v1/` возвращает корень router.

**Ограничения:**

- Аутентификация и permissions не заданы → API доступен анонимно, включая
  изменение и удаление (дефект D-06).
- Создание через API не работает для новой записи, так как `uid` обязателен в
  модели, но отсутствует в сериализаторе (дефект D-05).

**Подтверждение:** `dashboard/api/v1/router.py:5-6`, `dashboard/api/v1/views.py:16-22`, `dashboard/api/v1/serializer.py:6-19`, `config/settings.py:31-35`.

### UC-10. Импорт справочника акций

**Актор:** разработчик/администратор, запускающий management-команду.  
**Предусловие:** задан `TINKOFF_TOKEN`, доступен Tinkoff API.

**Поток:**

1. Выполняется `python manage.py add_shares`.
2. Команда открывает `Client(TINKOFF_TOKEN)`.
3. Получает список всех инструментов через `client.instruments.shares()`.
4. Для каждого инструмента выполняет `Share.objects.get_or_create(...)`.
5. Записи сохраняются в БД; цены и флаг тренда не заполняются.

**Подтверждение:** `dashboard/management/commands/add_shares.py:8-22`, `README.md:9-10`.

### UC-11. Фоновое обновление цен

**Актор:** система (Celery Beat + Worker).  
**Предусловие:** запущены Redis, Celery Beat и Celery Worker, задан токен.

**Поток:**

1. Celery Beat каждые 10 секунд публикует задачу `dashboard.tasks.update_last_price`.
2. Worker выбирает все записи `Share`.
3. Для каждой акции вызывает Tinkoff API и получает последнюю цену.
4. Сравнивает новую цену с сохранённой и вычисляет `is_trend_high`.
5. Обновляет `last_price` и `is_trend_high` через `QuerySet.update()`.

**Исключения:**

- Ошибка по одной акции логируется, цикл продолжается.
- `last_price = NULL` приводит к исключению сравнения, которое трактуется как
  `is_trend_high = True` (дефект D-10).
- `updated_at` не обновляется, так как `QuerySet.update()` обходит `auto_now`
  (дефект D-08).

**Подтверждение:** `config/celery.py:13-18`, `dashboard/tasks.py:7-28`, `dashboard/services/market_data.py:6-11`.

## 5. Функциональные требования

### 5.1. Каталог и карточка акции

#### FR-01. Просмотр каталога акций

## 8. Что не реализовано и не является требованием

Следующие возможности отсутствуют в исходном коде и поэтому **не включены** в
восстановленные требования:

- персональные списки наблюдения (watchlist);
- целевые ценовые уровни и уведомления;
- виртуальный инвестиционный портфель;
- учёт количества, средней цены, прибыли/убытков;
- история операций;
- история рыночных цен в БД;
- графики по накопленной истории;
- симулятор инвестиционных стратегий;
- автоматическое моделирование сделок;
- привязка акций, портфелей и watchlist к пользователю;
- роли и права кроме стандартных Django (`is_staff`, `is_superuser`);
- API-аутентификация по токену, OAuth, JWT;
- email-уведомления, push-уведомления, WebSocket;
- фоновое обновление справочника по расписанию;
- soft delete, аудит изменений, версионирование записей;
- хранение результата Celery-задач;
- тесты пользовательских сценариев и UI.

Это важно для задания №4: новые функции потребуют новых сущностей и связей
(`User` ↔ `Watchlist` ↔ `Share`, `Portfolio` ↔ `Position` ↔ `Share`,
`PriceHistory` ↔ `Share`, `Strategy` ↔ `Operation` и т.д.).
